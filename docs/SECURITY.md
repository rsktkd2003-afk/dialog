# セキュリティとデータ管理

## 1. 実装済みの対策

| 項目 | 内容 | 実装 |
| --- | --- | --- |
| パスワード | scrypt（N=2^15, r=8, p=1, 16バイトのソルト）。10〜128文字。NFKC 正規化 | `src/lib/auth/password.ts` |
| ログイン | 存在しないメールアドレスでもダミーのハッシュ検証を行い、応答時間の差を小さくする。エラーメッセージを共通化 | `src/lib/auth/service.ts` |
| ロックアウト | 10回連続で失敗すると15分ロック | 同上 |
| セッション | 32バイトの乱数トークン。DBには SHA-256 ハッシュのみ保存。HttpOnly・SameSite=Lax・本番は Secure。30日有効（残り15日未満で延長）。パスワード変更時は全セッションを無効化 | `src/lib/auth/*` |
| アクセス制御 | 全ページ・Server Action・API でサーバー側の `requireUser()`／`getCurrentUser()` を通す。データアクセス関数はユーザーIDを必須とし、すべての SELECT/UPDATE/DELETE の条件に含める。他人の食品・種目・テンプレート・メニューの ID を指定しても利用できない | `src/lib/repo/*` |
| CSRF | Server Actions は Next.js の Origin 検査の対象。クッキーは SameSite=Lax | |
| 入力検証 | Zod で型・範囲・形式を検証（例：体重 25〜250kg、存在しない日付の拒否、RPE 0.5刻み）。LIKE 検索の特殊文字をエスケープ。SQL は ORM のパラメータ化クエリ | `src/lib/validation.ts` ほか |
| オープンリダイレクト | 戻り先は固定値または `/meals/add?` で始まる値のみ許可 | |
| HTTP ヘッダー | X-Content-Type-Options・X-Frame-Options: DENY・Referrer-Policy・Permissions-Policy、X-Powered-By 非表示 | `next.config.ts` |
| データの持ち出し | 本人のデータを JSON でエクスポート（パスワードハッシュ・セッションは含めない）。キャッシュ無効 | `src/app/api/export/route.ts` |
| 削除 | パスワードと確認語の入力で、アカウントと全データを削除（外部キーの CASCADE） | |
| 管理者による閲覧 | アプリ内に管理者が他人の記録を見る画面・API は存在しない | |
| 外部送信 | 記録を外部AIサービス等に送信しない | |

| 不調記録 | 作成・取得・削除をすべてユーザーIDで絞り込み。エクスポートに含め、アカウント削除で CASCADE 削除。保存・削除時のエラーはエラー名とコードのみをログに出し、メモ等の入力値（クエリのパラメータ）は出力しない | `src/lib/repo/symptoms.ts`, `src/app/(app)/condition/actions.ts` |

テスト：`tests/auth.test.ts`、`tests/isolation.test.ts`、`tests/symptoms.test.ts`（他人のデータの参照・更新・削除・コピー・利用がすべて拒否されることを検証）

## 2. 残課題（未対応）

| 優先度 | 課題 | 対応案 |
| --- | --- | --- |
| 高 | 本番の HTTPS・DB 接続の暗号化（TLS）は未構築 | ホスティング・DB の選定後に設定。`DATABASE_URL` に `sslmode=require` |
| 高 | バックアップ・復旧手順が未整備 | マネージド DB の自動バックアップ（PITR）を有効化し、復旧手順を検証 |
| 高 | IP 単位のレート制限がない。アカウント単位のロックは、第三者が他人のメールアドレスでわざと失敗させてロックさせることにも使える | リバースプロキシ・ホスティング側のレート制限、または IP＋アカウントの組み合わせによる制限 |
| 中 | メールアドレスの確認・パスワードリセットがない | メール送信サービスの導入後に実装 |
| 中 | 登録が誰でも可能（招待制ではない） | チーム公開時に招待トークン方式を追加するか、登録を環境変数で制限 |
| 中 | Content-Security-Policy 未設定 | nonce を使った CSP を追加 |
| 中 | DB エラー時、サーバーログにクエリのパラメータ（入力値）が出力される可能性。体調・不調の Server Action では対策済みだが、他の画面の Server Action は未対策 | 共通のエラーハンドラーで同様にパラメータを除去。本番のログ出力先と保持期間を決める |
| 中 | 保存データの暗号化は DB サービスの保存時暗号化に依存。DB の運用者は技術的にはデータを閲覧できる | 運用者の DB アクセス権限を最小化し、アクセス記録を残す。必要に応じて列単位の暗号化を検討 |
| 低 | 開発用ツール drizzle-kit の依存（esbuild）に既知の脆弱性（開発サーバー関連）。本番依存（`npm audit --omit=dev`）は 0 件 | drizzle-kit の更新を待つ。本番環境には含めない |
| 低 | 期限切れセッションを定期削除する処理がない（関数 `deleteExpiredSessions` のみ） | 定期実行ジョブを設定 |

## 3. データ管理方針（案）

公開前に運営者が確定し、プライバシーポリシーに反映すること。

- **保持期間**：アカウントが存在する間は保持。アカウント削除時に即時削除。長期間ログインのないアカウントの扱い（例：2年で通知のうえ削除）を決める
- **バックアップ**：日次の自動バックアップ＋7日程度の PITR を推奨。削除済みデータがバックアップに残る期間をポリシーに明記
- **復旧**：バックアップからの復元手順を文書化し、公開前に1回は復元を試験する
- **ログ**：アクセスログ・エラーログに健康情報を残さない。保持期間を定める
- **アクセス権**：本番 DB に接続できる人を限定し、接続情報は環境変数（ホスティングのシークレット管理）でのみ扱う。`.env*` は Git 管理対象外
