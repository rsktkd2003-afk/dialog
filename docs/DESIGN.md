# 設計

## 1. 調査結果（作業開始時点）

- リポジトリは `README.md` のみの空の状態だったため、新規に構築した
- 開発環境：Node.js 22、PostgreSQL 16 のバイナリあり（Docker なし）
- 文部科学省のサイト（食品成分表）にはネットワーク制限で接続できなかった → 成分データは同梱せず、取込スクリプトのみ用意

## 2. 要件の整理

### 機能要件
初回プロフィール登録、個人別の目標算出、ホームダッシュボード、食事管理、筋力トレーニング管理、バレーボール競技記録、コンディション管理、分析、個別提案、複数ユーザー・チーム対応。

### 非機能要件
| 区分 | 要件 | 対応 |
| --- | --- | --- |
| 端末 | Android・iPhone のブラウザ、片手操作 | スマホ幅を基準にしたレイアウト、下部タブナビ、タップ領域 44px 以上、iOS のズームを防ぐ 16px 入力 |
| 入力負担 | 少ないタップ | 既定の分量で即「追加」、前日コピー、お気に入り・メニュー、テンプレート、練習時間・強度は普段の設定値を初期値に |
| 永続性 | データの永続保存 | PostgreSQL |
| 分離 | ユーザー単位 | すべてのデータアクセス関数がユーザーIDを必須とし、条件に含める（結合テストで検証） |
| 拡張性 | 将来の機能追加 | 計算・データアクセス・UIを分離 |
| 運用コスト | 低コスト | AI API を使わない。外部サービスは DB とホスティングのみ |
| アクセシビリティ | | ラベル付きフォーム、色だけに頼らない状態表示（アイコン＋ラベル）、グラフの表形式表示、ダークモード |

## 4. 技術選定

| 候補 | 評価 |
| --- | --- |
| **Next.js（App Router）+ PostgreSQL + 自前のセッション認証（採用）** | TypeScript で画面とサーバー処理を一体で書ける。Server Actions により API 層を別に作らずにサーバー側でアクセス制御できる。PostgreSQL はマネージドサービスが多く、移行しやすい |
| Next.js + Supabase（Auth・RLS） | 認証と行単位のアクセス制御を任せられるが、外部サービスの契約が前提。今回は契約前のため不採用。将来移行する場合も Postgres のため移しやすい |
| Next.js + Firebase | NoSQL で集計・相関の処理が書きにくく、ベンダー依存が強い |
| SPA + 別 API サーバー | 構成が増え、少人数での保守に向かない |

- ORM：Drizzle（型安全、SQL に近く、マイグレーションを SQL ファイルで確認できる）
- 認証：外部サービスに依存しないよう、パスワードハッシュ（Node 標準の scrypt）とセッション管理を最小限で実装。ライブラリの追加を避けた
- グラフ：表示が単純なためライブラリを使わず SVG で実装（依存とバンドルサイズを抑える）
- テスト：PGlite により、DB サーバーなしで実際の SQL・制約を検証できる

| recipe_items | レシピの材料 | |
| favorite_foods | お気に入り | |
| meal_entries | 食事記録（栄養値は記録時点のスナップショット） | |

| exercises | 種目（user が null なら共通種目） | |

## 7. 体調・不調の記録方式（2026-10 追加）

- 既存の `condition_logs` は1日1件・`discomforts` が JSON（部位6種・3段階）で、同日に複数の詳細記録を保存できないため、新テーブル `symptom_logs` を追加した
- 既存データは移行・変換しない（変換時の解釈違いでデータを失うのを避けるため）。旧形式は履歴画面で参照のみ表示し、提案ルール（痛みの案内）でも引き続き評価する
- 日常の体調フォームは `discomforts` を送らず、`upsertCondition` は `discomforts` が省略された場合に既存値を変更しない
- 提案ルール：新形式は直近7日の「痛み・しびれ（程度1以上）」または「動作が制限される／運動できない」、および同じ部位が直近14日で3日以上の場合に医療専門職への相談を案内する（`docs/CALCULATIONS.md`）
