# 設計

## 1. 調査結果（作業開始時点）

- リポジトリは `README.md` のみの空の状態だったため、新規に構築した
- 開発環境：Node.js 22、PostgreSQL 16 のバイナリあり（Docker なし）
- 文部科学省のサイト（食品成分表）にはネットワーク制限で接続できなかった → 成分データは同梱せず、取込スクリプトのみ用意

## 2. 要件の整理

### 機能要件
初回プロフィール登録、個人別の目標算出、ホームダッシュボード、食事管理、筋力トレーニング管理、バレーボール競技記録、コンディション管理、分析、個別提案、複数ユーザー・チーム対応。

### 非機能要件
| 区分 | 要件 | 対応 |
| --- | --- | --- |
| 端末 | Android・iPhone のブラウザ、片手操作 | スマホ幅を基準にしたレイアウト、下部タブナビ、タップ領域 44px 以上、iOS のズームを防ぐ 16px 入力 |
| 入力負担 | 少ないタップ | 既定の分量で即「追加」、前日コピー、お気に入り・メニュー、テンプレート、練習時間・強度は普段の設定値を初期値に |
| 永続性 | データの永続保存 | PostgreSQL |
| 分離 | ユーザー単位 | すべてのデータアクセス関数がユーザーIDを必須とし、条件に含める（結合テストで検証） |
| 拡張性 | 将来の機能追加 | 計算・データアクセス・UIを分離 |
| 運用コスト | 低コスト | AI API を使わない。外部サービスは DB とホスティングのみ |
| アクセシビリティ | | ラベル付きフォーム、色だけに頼らない状態表示（アイコン＋ラベル）、グラフの表形式表示、ダークモード |

## 3. MVPと将来機能

### 実装済み（MVP）
- アカウント登録・ログイン・ログアウト・パスワード変更・ロックアウト
- 4ステップの初回登録（すべて任意）
- 個人別の栄養目標算出と計算根拠の表示
- 食事記録（検索・分量・お気に入り・よく食べる食品・お気に入りメニュー・前日コピー・レシピ・お惣菜／外食・補助食品・栄養不明の記録・日別／週別推移）
- 筋トレ記録（左右別・RPE/RIR・休憩・前回記録・推定1RM・総負荷量推移・テンプレート・再利用・上半身／下半身区分）
- バレー練習記録・週ごとの練習負荷
- ジャンプ測定（実測／自己申告／推定の区別、ジャンプ高の算出）
- コンディション記録・痛みの案内
- ホームダッシュボード（最優先目標で表示順を変更）
- 相関分析（記録不足時は非表示）
- ルールベースの提案
- データのエクスポート・アカウント削除
- PWA マニフェスト（ホーム画面への追加）
- プライバシーポリシー（草案）

### チーム機能の設計案（未実装）
- `teams`（id, name, created_by）、`team_members`（team_id, user_id, role: admin/player, joined_at）
- `team_invites`（token_hash, team_id, expires_at, max_uses）— 招待URLのトークンはハッシュで保存
- `share_settings`（user_id, team_id, item: weight/jump/strength/practice/condition/nutrition, enabled）— 既定はすべて無効
- チーム画面のクエリは「メンバーであること」と「本人が共有を許可した項目であること」の両方をサーバー側で確認する
- チーム管理者であっても、共有されていない項目は取得できない（管理者用の閲覧APIを作らない）
- 現在のデータアクセス関数は `userId` を必須とする構造のため、この方針に沿って拡張できる

## 4. 技術選定

| 候補 | 評価 |
| --- | --- |
| **Next.js（App Router）+ PostgreSQL + 自前のセッション認証（採用）** | TypeScript で画面とサーバー処理を一体で書ける。Server Actions により API 層を別に作らずにサーバー側でアクセス制御できる。PostgreSQL はマネージドサービスが多く、移行しやすい |
| Next.js + Supabase（Auth・RLS） | 認証と行単位のアクセス制御を任せられるが、外部サービスの契約が前提。今回は契約前のため不採用。将来移行する場合も Postgres のため移しやすい |
| Next.js + Firebase | NoSQL で集計・相関の処理が書きにくく、ベンダー依存が強い |
| SPA + 別 API サーバー | 構成が増え、少人数での保守に向かない |

- ORM：Drizzle（型安全、SQL に近く、マイグレーションを SQL ファイルで確認できる）
- 認証：外部サービスに依存しないよう、パスワードハッシュ（Node 標準の scrypt）とセッション管理を最小限で実装。ライブラリの追加を避けた
- グラフ：表示が単純なためライブラリを使わず SVG で実装（依存とバンドルサイズを抑える）
- テスト：PGlite により、DB サーバーなしで実際の SQL・制約を検証できる

## 5. データベース設計

`src/lib/db/schema.ts`（マイグレーション：`drizzle/0000_init.sql`）

| テーブル | 内容 | 備考 |
| --- | --- | --- |
| users | メール・パスワードハッシュ・表示名・ログイン失敗回数・ロック期限 | |
| sessions | セッション（id = トークンの SHA-256） | 30日、残り15日未満で延長 |
| profiles | 生年月日/年齢・性別・身長・競技情報・運動習慣・曜日・目標・手動調整 | 1ユーザー1行 |
| body_measurements | 体重・体脂肪率（計測方法）・周囲径 | 履歴として追記 |
| jump_measurements | 種類・値・実測/自己申告/推定・靴・測定方法 | |
| foods | 食品（owner が null なら共通食品）・基準（100g/1食）・栄養値（null＝不明）・出所 | 削除せず非表示（archived） |
| recipe_items | レシピの材料 | |
| favorite_foods | お気に入り | |
| meal_entries | 食事記録（栄養値は記録時点のスナップショット） | |
| meal_sets / meal_set_items | お気に入りメニュー | |
| exercises | 種目（user が null なら共通種目） | |
| workouts / workout_sets | ワークアウトとセット（左右・RPE・RIR・休憩） | sets にも user_id を持たせて二重に絞り込み |
| workout_templates | テンプレート（JSON） | |
| practice_sessions | バレー練習 | |
| condition_logs | コンディション（1日1件、違和感は JSON） | |

- すべての個人データは `users` への外部キーで ON DELETE CASCADE（アカウント削除で全削除）
- 日付は利用者の日本時間の日付（`date` 型）で保存

## 6. 画面構成とユーザーフロー

```
/register → /onboarding?step=1..4（スキップ可）→ /onboarding/done（目標と根拠）→ /
/login → /（初回登録が未完了なら /onboarding）

下部タブ：ホーム / 食事 / 筋トレ / 練習 / 体・分析
  ホーム        /            今日の目標・提案・各カード（最優先目標で並び替え）、設定へのリンク
  食事          /meals       日付切替・合計・食事区分ごとの記録
                /meals/add   検索・お気に入り・メニュー・よく食べる食品・登録なし記録
                /meals/trends, /foods, /foods/new, /foods/recipe
  筋トレ        /training    テンプレート・最近の記録・種目
                /training/new, /training/[id], /training/exercise/[id]
  練習          /practice    記録フォーム・週ごとの負荷・履歴
  体・分析      /body        身体指標・推移・ジャンプ・測定履歴
                /body/new, /body/jump/new, /condition, /analysis
  設定          /settings    プロフィール編集・計算根拠・手動調整・エクスポート・パスワード・削除
```
